# 扩大邻域时只执行新增撒点

去重的单位是 `{Hash[operator,"SHA256"], seed}`，不是中心积分。同一 seed 对不同 IBP 算符仍是不同应用；不同中心产生相同算符/seed 时只执行一次。已生成关系继续保留在方程池里，不能因为不再撒点而删去旧关系。

0.2.2 将筛选前移到主进程：

1. 对合并后的目标作指定的域内 symmetry-image 处理，并只枚举一次候选邻域。
2. 形成算符/seed 批次，减去 `CompletedApplications`，再去掉本批次内部的重复应用。
3. 将剩余批次分发给 worker；worker 不再各自重新枚举全部邻域。完全重合且没有额外有限组合 seeds 时不启动 worker，但仍处理必要的新 symmetry 关系。
4. 新完成的应用加入累计台账。定向缺口补点后的扩大邻域使用更新后的台账。

`SeedingDeduplication` 返回普通 G 撒点的候选数、已完成而跳过数、本批重复数和待执行数。
额外 `FiniteSeeds` 也按同一个应用键检查完成记录，其数量不混入名称带 `OrdinaryApplications` 的统计字段。

专项测试验证：扩大的邻域存在实际重叠；串行与并行一致；增量应用集合等于完整新邻域减去已有集合；新旧方程并集与不去重的完整生成结果完全相同；全重叠时启动 0 个 worker；重复算符不会重复执行同一应用。

## 台账与迁移

同一版本的 checkpoint 持续保存 `CompletedApplications`。只有方程池而没有撒点台账时，不能凭方程条数推断哪些应用已经完成；同样不能在 family 或 IBP 构造改变后盲目复用台账。

本次四圈 0.2.0 → 0.2.2 的特定迁移额外核验：两个检查点内容哈希、各自实现哈希、family 完全一致、IBP 构造和 symmetry 代码逐字相同，以及继承台账对应的整个方程池完整保留。通过后才恢复历史应用记录；这不是放宽一般 `ResumeRun` 的实现哈希检查。

正在执行的旧批次在已验证约化检查点处被替代；未完成 worker 不记入完成台账。新批次仍需经过后续完整约化及精确残差验证。

本次四圈实际批次：44,766 个候选普通应用，跳过历史完成的 27,358 个，仅分发 17,408 个；削减约 61.1%。此为应用数减少比例，不是完整 DE 求解时间的加速比。

0.2.3 补充：父进程在判断活跃算符时，也查询有限组合应用的完成账本。普通应用和有限组合应用均已完成时不启动 worker；仍有待执行有限组合时照常启动。该修改不改变生成的关系及应用集合，当前四圈运行仍使用冻结的 0.2.2。
